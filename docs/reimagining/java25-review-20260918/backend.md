# Backend review — 2026-09-18

Reviewed all **157 assigned files / 24,893 manifest lines**: 90 production files and 67 test files. Baseline: `91b9bd74746d27102a96fa47d4e06e0dd25097ca`. The adjacent JSONL records each file and its manifest SHA-256. This was one source review pass, with tests and selected callers inspected; no builds, tests, implementation changes, or runtime measurements were performed. Findings below distinguish observable source defects from design choices. Account usage percentage was unavailable.

The current direction is sound: keep the original `SchedulerMain`, seven store interfaces, SQLite transactions, and Go execution adapter. Small execution interfaces express useful capabilities; records already fit immutable observations and commands. In particular, retain the explicit byte-array ownership/equality in `SqliteEffects.Command`, transaction-scoped JDBC access, rollback-only propagation, ownership locks, commit uncertainty, post-commit event ordering, Stop priority, cleanup reservations, and retirement fences. Do not replace these with generic repository/async layers or a second scheduler. Java 25 does not justify replacing every callback, Guava type, or mutable lifecycle holder with a record or stream.

## Highest-value coordinated improvements

### BACK-001 [P2] — Split the Go driver along protocol responsibilities, preserving its transaction choreography

**Design choice; high value.** `src/main/java/org/apache/aurora/scheduler/execution/go/GoAgentDriver.java:149`, `:317`, `:574`, `:871` put log routing, watch consumption, capacity offers, and the retirement handshake in a 1,012-line service. Retirement alone manipulates authorization intervals as mutable `long[]`, validates agent responses, and deletes durable history. These are independently understandable responsibilities with different invariants.

Extract package-private log reader and retirement coordinator first; give retirement a validated immutable interval value and pure interval operations. Keep the driver as lifecycle/orchestration owner and keep network calls between, never inside, durable transaction phases. Avoid a public plugin framework. Watch/dispatch decomposition can follow only if it makes lock ownership clearer. Preserve snapshot readiness, acknowledgement-after-commit, Stop tombstones, and late-response retirement handling. Future validation: retain all driver race/replay tests, especially lost retirement replies, unauthorized ranges, blocked Run versus Stop, and cleanup capacity; add direct interval boundary tests. The existing `GoAgentDriverTest` and `GoTaskLogsTest` provide useful seams.

### BACK-002 [P2] — Reduce full-store decoding and all-agent wakeups on the scheduling path

**Performance/design choice; high value, unmeasured.** `src/main/java/org/apache/aurora/scheduler/storage/sqlite/SqliteTaskStore.java:48` only specializes task-ID queries; every other filter decodes every task. `src/main/java/org/apache/aurora/scheduler/storage/sqlite/SqliteJobUpdateStore.java:45` similarly decodes all histories for a plural `fetchJobUpdates` query constrained to one update key; the singular `fetchJobUpdate` already reads one record at `:51`. `SqliteRecords.java:85` decodes eagerly before filtering. `src/main/java/org/apache/aurora/scheduler/execution/go/GoAgentDriver.java:243`, `:312`, `:574` amplify this: each task event releases every agent's wake semaphore (`:314`), and each ready inventory refresh compares a full-store read filtered by agent (`:248`). Refresh conditionally recalculates an offer (`:251`); if capacity/reservation checks pass, this scans again in a write transaction (`:595`). Wake permits coalesce (`:284`), so this is not a claim of two scans per event. The shared concurrency test explicitly documents a million decoded records (`src/test/java/org/apache/aurora/scheduler/storage/AbstractTaskStoreTest.java:597`).

First add the exact-key job-update query fast path (still applying all other predicates and pagination) and target task-change wakes to the affected agent where the event identifies it. Then measure realistic task counts before introducing minimal transactional task projections/indexes for host/job/status. Keep the Thrift blob authoritative and the existing query predicate as the semantic reference; migrate/rebuild indexes transactionally. Preserve capacity subtraction for scheduler-active tasks and agent reservations, including pruned tasks with unfinished cleanup. Future validation: shared task query suite, index mutation/reopen parity, multi-agent scheduling, and allocation/latency measurements. Do not add an independently mutable cache as a shortcut.

### BACK-003 [P2] — Stop doing legacy reconciliation work that the Go backend discards

**Design choice.** `src/main/java/org/apache/aurora/scheduler/reconciliation/TaskReconciler.java:138`, `:153` schedule periodic scans and delayed batches, while `src/main/java/org/apache/aurora/scheduler/execution/go/GoAgentDriver.java:993` intentionally ignores every reconciliation request. This is installed by `src/main/java/org/apache/aurora/scheduler/app/AppModule.java:177`; the original entrypoint installs `GoAgentModule` at `src/main/java/org/apache/aurora/scheduler/app/SchedulerMain.java:175`. The no-op is correct for watch reconciliation, but its caller still pays for full SQLite decoding and counts apparent runs.

Make reconciliation strategy explicit at this seam: skip legacy scan/batching for watch-based reconciliation, or have an intentional backend operation whose semantics are defined. Keep existing Thrift methods/signatures and input validation (`src/main/java/org/apache/aurora/scheduler/thrift/SchedulerThriftInterface.java:674`); do not silently turn an administrative call into task-loss inference. Keep TaskTimeout and KillRetry as separate existing policy controllers. Future validation: verify Go mode performs no scan or delayed batch for these triggers, preserves RPC compatibility, and reconnect snapshots remain the reconciliation authority.

### BACK-004 [P2] — Isolate obsolete writable log infrastructure from required historical import

**Design choice; coordinated removal, not a blanket deletion.** The current scheduler binds SQLite in `src/main/java/org/apache/aurora/scheduler/execution/go/GoAgentModule.java:66`; no production construction of `DurableStorageModule`, `LogPersistenceModule`, `SnapshotModule`, or `BackupModule` was found. The only `Log` implementation in the tree is the test `FakeLog`. Yet the main source set retains the writable durability recorder, framing/compression/checksum pipeline, scheduled log snapshots, online editable recovery, and associated Guice modules. In contrast, `src/main/java/org/apache/aurora/scheduler/storage/sqlite/SqliteRecovery.java:189` genuinely uses `BackupReader`, `SnapshotterImpl`, `Loader`, and `ThriftBackfill` for offline historical import.

Document and separate the read/import compatibility surface, then remove or move uninstantiated writable-log infrastructure and its exclusive tests after confirming packaging/custom module support. Keep public backup/recovery contracts needed by the Thrift API and the Go adapter's offline-only rejection. Retain historical schemas/goldens and loader/backfill behavior; do not infer that old formats can be deleted because old writers can. Future validation: original entrypoint injection, offline snapshot import, complete SQLite restore, and compatibility goldens. This offers more simplification than modernizing every legacy implementation in place.

### BACK-005 [P3] — Extract SQLite schema and backup mechanics, not the transaction state machine

**Design choice.** `src/main/java/org/apache/aurora/scheduler/storage/sqlite/SqliteDatabase.java:275` contains schema upgrades and owner activation; `:491` contains filesystem backup publication/verification; `:583` contains the nested transaction, fencing, commit, and publication machinery. The latter is subtle but cohesive, and its explicit cleanup logic is justified by uncertain commit and failed-close tests.

Extract a package-private schema migrator that runs on the caller's connection within the existing `BEGIN IMMEDIATE`, and a backup helper invoked while the same owner/writer/lifecycle guards are held. SQL text blocks can make fixed DDL readable without a schema DSL. Keep connection quarantine, ownership release, outcome receipts, and publication order in the database owner. Do not mechanically replace custom close handling with try-with-resources: committed-close failures intentionally have special meaning. Future validation: existing migration rollback, anchor close, disk-full rollback-only, crash, uncertain commit, and atomic backup tests, with unchanged failure classification.

## Local improvements and concrete defects

### BACK-006 [P2] — Scheduled reconciliation/timeout work outlives service shutdown

**Concrete lifecycle defect; bounded shutdown impact.** `src/main/java/org/apache/aurora/scheduler/reconciliation/TaskTimeout.java:116` treats every non-RUNNING state as pre-start and reschedules indefinitely; after TERMINATED/FAILED it can never become RUNNING. `src/main/java/org/apache/aurora/scheduler/reconciliation/TaskReconciler.java:172` does nothing on shutdown even though `ReconciliationModule.java:153` creates its private scheduler and recurring/batched futures are never cancelled. Shutdown can therefore leave unnecessary timer activity or callbacks attempting storage access until executor/VM shutdown. These workers are daemon threads (`src/main/java/org/apache/aurora/scheduler/base/AsyncUtil.java:61`), so they do not prevent JVM exit; the defect is work continuing after the service reports itself stopped.

Use an explicit service-state switch: retry only NEW/STARTING, run only RUNNING, stop for terminal/stopping states. Track/cancel reconciler futures or shut down the privately owned executor with bounded cleanup; never shut down TaskTimeout's shared `@AsyncExecutor`. Preserve startup recovery events and the state-CAS timeout guard. Future validation: extend `TaskTimeoutTest` beyond its existing not-started case and extend `TaskReconcilerTest` to advance the fake scheduler after stop; assert no storage access or rescheduling. This is a lifecycle fix, not permission to infer Go task loss from missed heartbeats.

### BACK-007 [P3] — Validate watch trees without deep-copying and canonicalizing them

**Local performance/simplification choice.** `src/main/java/org/apache/aurora/scheduler/execution/go/WireJson.java:59` traverses for depth, deep-copies the frame, rewrites diagnostic `exitCode=-1`, then calls `bytes`, which constructs another sorted tree and serializes bytes only to discard them. This happens on every watch frame from `GoAgentClient.java:150`.

Implement a non-mutating validation walk with the exact diagnostic-path exception; share scalar/key validation with canonical command encoding. Keep canonical serialization exclusively where bytes/hashes are needed. Preserve printable-ASCII, depth, safe nonnegative integer checks, and the sole permitted -1 execution diagnostic. No generic Jackson binding or relaxed validation is needed. Future validation: existing `WireJsonTest` and `GoAgentClientTest` numeric/path/depth cases, plus confirmation input nodes remain unchanged and a representative allocation measurement. This is not a finding against the recently fixed signal-exit behavior.

### BACK-008 [P2] — Parse the Go process profile once into a validated internal value

**Local abstraction choice.** `src/main/java/org/apache/aurora/scheduler/execution/go/GoTaskFactory.java:52`, `:87`, `:158`, `:177` repeat parsing/validation across admission, prepare, and health-port lookups. Preparation validates (which parses), then immediately parses again; capacity and placement paths also parse the full executor payload just to find a socket.

Introduce a package-private validated process-profile value with immutable argv/env and optional health details, returned by one parser. Use it within each operation for validation, launch assembly, and socket extraction. Keep task-wide resource/tier policy separate and preserve explicit JSON construction/canonical hashing and ASCII constraints. Avoid an unbounded global cache or changing the public executor-data wire format. Future validation: current profile rejection and launch-shape tests, byte-for-byte equivalent canonical Run payloads, health socket conflicts, and offline import acceptance/rejection. A record is useful here because it represents validated data, not merely because Java supports records.

### BACK-009 [P2] — Correct the final-golden omission in compatibility replay

**Concrete test defect.** `src/test/java/org/apache/aurora/scheduler/storage/durability/DataCompatibilityTest.java:171` uses `IntStream.range(1, goldenOps.size())` and replays `subList(0, i)`. The last historical golden is never replayed. The earlier sanity run uses current generated operations, so it does not cover this missing historical record.

Use an inclusive upper bound or a plain loop through `size()`, preserving prefix order and the diagnostic pointing at the newly introduced operation. Future validation: arrange for the last golden to fail decoding/replay and confirm the test fails, then restore the fixture. Keep this coverage when separating historical import from writable-log infrastructure.

### BACK-010 [P2] — Repair storage tests that discard or collapse the cases they claim to check

**Concrete test defects.** `src/test/java/org/apache/aurora/scheduler/storage/AbstractJobUpdateStoreTest.java:164` changes a builder to extreme CPU/RAM/disk values, but `:171` constructs a fresh ordinary update and saves that. Build the update from the modified builder and assert the resource values after reload. Separately, `src/test/java/org/apache/aurora/scheduler/storage/AbstractTaskStoreTest.java:430` creates three identical tasks with ID `a`; the Set collapses them, and later value-based Set collection collapses equal configs before the identity map check. It does not demonstrate interning across distinct tasks.

Use distinct task IDs sharing equal configs, and test identity only in the memory-specific suite if that implementation contract is intentional; keep value equality as the cross-backend storage contract. Future validation: run both inherited Mem/SQLite store suites for extreme values; prove the memory interning test fails when canonicalization is disabled. Do not impose Java reference sharing on SQLite's detached deserialized values.

### BACK-011 [P3] — Make memory task replacement own index/interner updates once

**Concrete retained-memory defect plus local simplification; not the production SQLite backend.** `src/main/java/org/apache/aurora/scheduler/storage/mem/MemTaskStore.java:166` creates a lazy, side-effectful transform consumed once for the map and again per index. `:269` removes the association for the incoming config, never the replaced config. Replacing a task's config leaves the old config associated with its ID; deleting the task removes only the new config. `saveTasks` also inserts secondary indexes without removing the replaced task's old keys, unlike `mutateTask` at `:215`. `fromIdIndex` rechecks current tasks against the predicate (`:229`), masking stale memberships in ordinary filtered lookups; the retained index memberships and stale job keys exposed by `getJobKeys` (`:153`) remain concrete defects.

Centralize replacement around the actual previous task: remove its old associations/index entries, create one canonicalized replacement, and insert it once. Materialize a batch once or use a straightforward loop; keep the documented memory-store consistency model and ID collision checks. The existing overwrite test changes config bytes without checking released associations or changed job/host keys. Future validation: save/mutate across different configs, host/job-key overwrite followed by deletion, and verify interner/index size returns to zero. If BACK-004 makes this store test-only, fix or simplify it there rather than promoting it back into production storage.

## Coverage and uncertainty

Findings were checked against current tests and callers, not copied from the September 11 audit. Ledger verdicts: 99 retain, 10 local, 48 coordinated, 0 not-reviewed. A bounded second source check confirmed the SQLite scan, driver wake/offer, shutdown, and memory replacement findings; the descriptions explicitly distinguish singular update lookup, conditional/coalesced scans, daemon shutdown impact, and predicate-filtered stale indexes.

No runtime performance claims were measured, no tests were executed, and this pass is not a proof of cross-language protocol correctness. The largest residual risks in future changes are lock/transaction ordering, byte-exact identity, historical compatibility, and task reservations after ambiguous execution. SQLite restore intentionally preserves opaque positive effect payload versions; do not “tighten” that into an incompatible migration without defining the contract. Java 25 preview APIs, structured concurrency, ScopedValue, and wholesale Guava/JUnit migrations are not prerequisites for these recommendations.
