# Removing Aurora's Mesos dependency

Research date: 2026-09-09, America/New_York. Planning deliverable; no implementation or runtime validation is claimed.

## Recommendation and scope

Keep Aurora's Java scheduling policy, task state machine, update controller, quota model and public API initially. Replace Mesos execution with one standalone Aurora node agent per Linux host. Replace the Mesos replicated log with SQLite for the single-scheduler Raspberry Pi profile; use PostgreSQL for a later production HA profile. Make transactional state and reliable command dispatch prerequisites for real workloads. Do not write a new consensus algorithm.

The node agent is analogous to kubelet in responsibility: converge local execution toward durable assignments, admit only work the host can support, and report observed state. It is not a standalone kubelet deployment or an implementation of the Kubernetes API. Kubernetes separates cluster control from worker execution; CRI specifically connects kubelet to a container runtime, so CRI alone would not replace Aurora's scheduler-agent protocol. [Kubernetes architecture](https://kubernetes.io/docs/concepts/architecture/), [CRI](https://kubernetes.io/docs/concepts/containers/cri/).

Two independently removable dependencies exist:

1. **Execution:** framework registration, offers, resource allocation, launch/kill, executor delivery, statuses, reconciliation, and container isolation.
2. **Scheduler durability:** Aurora's own state transactions and snapshots written through Mesos's native replicated-log library. This is separate from the Mesos master's task registry and from ZooKeeper election/discovery.

Removing either does not remove the other. Removing both also does not automatically remove ZooKeeper or Thermos checkpoints. The final minimal Pi profile can omit ZooKeeper using a configured scheduler address and no service announcer; deployments relying on ServerSets need an explicit discovery migration.

**Assumptions:** initially one Aurora cluster owns each worker's allocatable resource pool; workloads are trusted experiments on the Pi; maintenance downtime is acceptable there; no automatic scheduler failover or workload-volume replication is required for that profile. Production HA, strict singleton workloads, untrusted tenancy, GPUs and complex network/storage plugins are separate acceptance gates. These are proposed scope boundaries, not observed user workload requirements.

## Minimal architecture and ownership

```text
Aurora CLI/UI -> scheduler API -> policy/state machine -> transactional store
                                     |                      |
                                node registry          durable outbox
                                     |                      |
                                     +-- authenticated scheduler-agent RPC --+
                                                                            |
                                                node agent: admission + journal
                                                                            |
                                                       runner/runtime -> workloads
```

The scheduler owns desired job state, instance generations, placement reservations, quotas, updates, cron templates, maintenance, command intent and durable observation cursors. The agent owns local resource enforcement, runtime identities, actual process state, status replay, logs and cleanup. Application data remains the workload's responsibility. Neither scheduler SQL nor agent journal replicates a workload's files.

Keep first-fit/group scheduling initially. Introduce neutral `NodeId`, `NodeInventory`, `Allocation`, `TaskSpec`, `TaskObservation` and `ExecutionBackend` interfaces. These are proposed new types, not existing repository classes. A temporary Mesos backend implements them, keeping legacy protobuf conversion in one module. The new backend uses node inventory directly.

Node inventory includes stable enrollment ID, boot/incarnation ID, architecture, supported spec/runtime capabilities, host/attribute labels, maintenance state, total/allocatable resources, ports and current allocations. Treat utilization as telemetry, not free allocatable capacity. Scheduler accounting subtracts all durable reservations, including launches whose acknowledgements are missing; agent independently verifies capacity immediately before acceptance. Standardize CPU units and rounding, memory/disk bytes, port sets and device identities. Converting legacy MiB and fractional CPU must never round a limit down below a request.

For the first Pi slice, support trusted process execution, CPU/memory limits, named host ports, disk accounting with an explicit enforcement policy, readiness and graceful termination. Reserve OS/agent overhead separately from per-task runner overhead. Validate Linux/cgroup support on the Pi during implementation. No GPU, revocable capacity, AppC, arbitrary Docker parameters or image-fetch compatibility is implied. Unsupported features fail admission rather than silently degrading. An OCI runtime path can follow behind the same task contract; detailed runtime choice belongs to the Go-agent plan.

## Removing the replicated log safely

**Yes, the Mesos replicated log can be removed.** `Persistence` already separates recovery and atomic batches of `Op` records from native log storage. `DurableStorage.doInTransaction` mutates volatile stores before `persist`; nested calls share the recorder. `MemStorage` supplies no rollback. [Persistence](../../src/main/java/org/apache/aurora/scheduler/storage/durability/Persistence.java), [DurableStorage](../../src/main/java/org/apache/aurora/scheduler/storage/durability/DurableStorage.java), [existing transaction tests](../../src/test/java/org/apache/aurora/scheduler/storage/mem/StorageTransactionTest.java).

Replacing only `LogPersistence` with a SQL table containing ordered Thrift transaction blobs is a useful bounded migration experiment: one SQL transaction per outer write; retain `Loader` and import/export compatibility. It does **not** create rollback for Aurora's in-memory mutations, isolate readers, or atomically dispatch launch/kill. Keep such a bridge nonproduction and fail the process closed on mutation/persistence errors; it is not the recommended final store. Current native-log failure shutdown is visible in [MesosLog](../../src/main/java/org/apache/aurora/scheduler/log/mesos/MesosLog.java).

The recommended working implementation is transactional SQL behind `Storage` and store interfaces. Use indexed identity/state columns plus versioned serialized payloads initially, avoiding a simultaneous complete Thrift redesign. Proposed tables: cluster metadata/epoch; nodes; jobs/cron templates; tasks and task events; quotas; job updates and update/instance events; maintenance requests; allocations/ports; command outbox; observation cursors and terminal tombstones. Preserve predecessor/failure history, configuration equality and update instructions. Enforce uniqueness for the scheduler's current active attempt per job/instance, while retaining separate records for uncertain old executions.

One outer `Storage.write` is one database transaction; nested writes reuse its connection and propagate failure. Multi-store reads use a consistent transaction snapshot. Caches publish only committed values. A state transition, replacement insertion, resource reservation and outbox command belong to the same commit when causally linked. Durable events or reconstructible after-commit notifications replace effects emitted before commit. Controllers still re-read state because asynchronous events can be stale. This requires reviewing every side-effecting `StateManager` action, not only replacing the database driver.

### Single scheduler on Raspberry Pi

Use SQLite on local persistent storage with WAL mode and `synchronous=FULL`, verify those settings at startup, keep bounded transactions and checkpoint monitoring, and enforce one scheduler process with an OS lock. SQLite WAL supports concurrent readers but one writer and requires same-host shared-memory coordination; it must not be placed on a network filesystem. FULL syncs the WAL at commits. [SQLite WAL](https://www.sqlite.org/wal.html).

Take backups through SQLite's backup API or a properly quiesced procedure, verify restoration, and retain off-host copies. Copying only the live main database file can omit WAL state. [SQLite backup API](https://www.sqlite.org/backup.html). Prefer reliable local storage and test actual power-loss recovery; this report did not inspect the Pi's disk or verify its flush guarantees. Select and pin a maintained SQLite/JDBC build with ARM64 coverage during implementation; no version is selected here.

This provides crash recovery of committed scheduler state on the surviving disk, not HA. The Pi and its disk remain failure domains. Restart recovers state, increments a durable scheduler epoch, reconstructs controllers/timers, and reconciles agents before releasing uncertain allocations. Disk loss requires restoration and a recovery barrier. No quorum, ZooKeeper election or remote failover is needed for this scope. Prototype acceptance target: restart and converge within 60 seconds for a documented small fixture; measure and revise before promising an SLO.

### Production HA

Use PostgreSQL as the authoritative store with one active scheduler and warm standbys. Reuse the SQL logical model; isolate dialect details and run the same store conformance suite. Ordinary asynchronous PostgreSQL replication can lose acknowledged transactions on primary failure. For an RPO-zero target within a defined failure envelope, require synchronous durable replication and promote only an eligible replica containing all acknowledged commits; do not automatically weaken durability when a standby is unavailable. [PostgreSQL replication](https://www.postgresql.org/docs/current/warm-standby.html).

Scheduler election and database failover are different problems. Elect a scheduler using a dedicated database session holding a cluster-specific advisory lock, then increment an epoch in committed metadata. PostgreSQL session locks last until release/session end. [PostgreSQL locking](https://www.postgresql.org/docs/current/explicit-locking.html). Mutating transactions must verify the current epoch, serialize against epoch change, and use the valid leader session; read-only health checks or a cached boolean are insufficient. Losing that session stops new mutations and dispatch. A wedged session can delay failover; configure and test bounded detection, accepting unavailable scheduling while ownership is uncertain.

A database HA mechanism must separately fence the former primary before promotion and prevent stale reads/writes through the old endpoint. PostgreSQL's failover documentation explicitly requires preventing two primaries and does not supply the surrounding failure-detection machinery. [PostgreSQL failover](https://www.postgresql.org/docs/current/warm-standby-failover.html). Choose an operationally supported HA deployment as an implementation prerequisite, rather than assuming advisory locks span independently writable primaries.

Every command includes cluster incarnation, scheduler epoch and exact attempt identity. Agents persist the highest accepted epoch and reject older commands. **That alone does not fence an isolated agent that has never observed the new epoch.** A new scheduler must retain its uncertain allocations and refrain from unsafe replacement until it has fenced/reconciled that execution. Scheduler election protects control-plane writes; workload fencing protects actual external side effects. A production claim needs both, plus backup/PITR, restore exercises, event retention and a stated failure envelope. A single PostgreSQL server improves transactional storage but is not HA.

An embedded replicated database or an etcd-backed design is plausible, but would require a new storage mapping, query/index strategy and operational recovery story. Adding a second coordination store beside PostgreSQL creates another consistency boundary. Prefer the two explicit profiles above; do not turn the Pi into a miniature consensus cluster merely to demonstrate restart persistence.

## Scheduler-agent contract and failure semantics

Use a versioned protobuf/gRPC contract over mutually authenticated TLS, preferably an agent-initiated connection to a configured scheduler endpoint. This is a proposal; gRPC transport does not provide durable delivery or exactly-once effects. Bind certificates to enrolled node IDs, reject wrong cluster IDs and unsupported major versions, negotiate capabilities, bound message/batch sizes and use retry backoff. Agent RPC does not expose arbitrary administrator commands.

| Message/operation | Required semantics |
| --- | --- |
| Register / reconnect | Node ID, boot ID, journal incarnation, capabilities, inventory generation, prior status cursor and complete allocation digest. An empty replacement disk is a new incarnation, never evidence that an old execution was stopped. |
| Heartbeat / inventory | Capacity, pressure, maintenance and observed allocations. Provisional starting values: heartbeat every 5 seconds, suspect after 3 missed heartbeats; these are fault-test parameters, not proven optimal defaults. A complete inventory is paginated under one snapshot ID/generation and applied only after all pages arrive. |
| Start attempt | Cluster incarnation, epoch, command ID, unique attempt ID, job/instance generation, node incarnation, allocation ID/version, immutable spec hash, resolved resources/ports and supported payload. Scheduler commits intent before sending. Agent atomically journals acceptance and reserves capacity before starting a deterministic runtime identity. |
| Start result | Durable ACCEPTED, retryable admission rejection, or permanent spec rejection with reason. Acceptance is not RUNNING. Exact duplicate ID/hash returns the prior result; same ID with different content is a conflict. Uncertain delivery retries the same attempt/command, not a replacement attempt. |
| Stop attempt | Exact attempt ID and desired terminal intent, command ID/epoch, grace deadline and reason (kill/restart/drain/preempt). Persist stop intent even if start has not arrived; a reordered late start cannot resurrect a tombstoned attempt. Completion means the runtime is confirmed stopped, not merely signal delivery. |
| Task observation | Attempt/node incarnations, monotonic per-attempt sequence, phase/readiness, terminal cause, exit result and resource/diagnostic metadata. Journal before sending; replay until the scheduler commits state and acknowledges a contiguous durable sequence. Bound history with acknowledged compaction and terminal retention. |
| Reconcile / query | Scheduler requests exact attempt states and full node snapshots; node reports running, terminal, accepted-not-started, definitely absent after local recovery, or unknown. Missing pages, failed runtime inspection and network timeouts cannot mean absent. |
| Forget / GC | Explicit acknowledgement plus retention horizon permits deleting logs/old journal details. Retain compact tombstones or a durable generation watermark so delayed commands cannot recreate completed attempts. New node identity is required after irrecoverable journal loss. |

Start has a journal-to-runtime crash window. The Go-agent design must close it with a deterministic runtime identity and recovery/adoption procedure: replay detects an already created process/container and adopts it instead of launching again. If identity cannot be established, quarantine the attempt and report uncertainty. A database write plus `fork()` is not an atomic operation.

Map accepted/startup to ASSIGNED/STARTING and report RUNNING only when the runner and configured health conditions permit it. Translate success, failure, resource violation and intentional termination into existing state-machine effects; preserve service replacement versus successful batch completion, failure budgets, throttling and update stability periods. A terminal observation never resurrects an old attempt. Preserve KILLING intent across PARTITIONED and restart; do not let old partition timers override newer state.

| Failure | Required outcome |
| --- | --- |
| Scheduler crashes before transaction commit | No new command was dispatched; rollback exposes no partial assignment or replacement. |
| Scheduler crashes after commit or after agent accepted, before reply | Outbox/reconciliation resends the same identity; one local execution, eventual state convergence. |
| Status commit succeeds but acknowledgement is lost | Agent replays; deduplication prevents duplicate task effects and replacement attempts. |
| Agent restarts, runtime survives | Recover journal, inspect runtime and adopt exact attempts before admission; replay retained statuses. |
| Agent dies during acceptance/start | Recover deterministic runtime identity; either resume creation safely or report uncertainty. Never guess based only on a PID. |
| Node is unreachable | Mark execution uncertain/PARTITIONED; stop placement on stale inventory. Preserve resource reservations. Continue local supervision by default; transport loss does not itself prove termination. |
| User kills an unreachable attempt | Persist kill tombstone and desired state; retry on reconnect. API exposes that physical termination is unconfirmed. Explicit kill does not accidentally become a service replacement. |
| Stale leader sends delayed command | Agent rejects older observed epoch. During leader takeover, connected nodes establish the new epoch before admission; disconnected nodes stay uncertain and block strict replacement. |
| Node returns after replacement under an availability policy | Reject/adopt according to exact attempt identity; terminate superseded execution, retain audit history and acknowledge terminal state without a kill/status loop. |
| Agent disk/journal is lost | Quarantine/re-enroll and inventory or fence surviving workloads before accepting work. Empty journal alone cannot authorize duplicate launch. |
| Database unavailable, full, corrupt or commit outcome unknown | Stop new scheduling/dispatch; agents retain current workloads and journal statuses with bounded backpressure. Resolve uncertain commits by command identity after recovery. Never acknowledge uncommitted status. |

Two explicit partition policies are necessary. **Safety-first (recommended new default):** wait for confirmed termination, physical node fencing, or a separately proven workload lease before launching a replacement elsewhere. **Availability-first (legacy-compatible opt-in):** replace after the configured timeout and admit that the old execution may still run. Existing absent `PartitionPolicy` can imply immediate replacement; migration must flag that difference for each job. An agent self-expiring lease is not a strict fence without bounded-clock/watchdog assumptions and verified termination; use an external resource fencing token or physical fencing when singleton side effects matter. Neither profile promises exactly-once application effects or exactly-once cron firing.

For state migration, freeze writes/update/cron activity, create a consistent snapshot, import into an isolated SQL database and reconcile all retained state. | Counts and semantic hashes match for every store; only one backend owns each worker pool/job generation. First native launch follows verified old termination or approved availability policy. |
| 6. Production HA | PostgreSQL store conformance, scheduler election/epochs, database fencing and eligible promotion, production security/runtime gates, backup/PITR and recovery runbooks. | Network partition and stale-primary tests demonstrate no unfenced control-plane writer; strict workloads never replace uncertain execution. Measured RPO/RTO meet declared goals under stated failures. |
| 7. Remove artifacts | Retire Mesos adapter, native library/egg, log framing path and obsolete settings/docs after rollback period. Keep historical snapshot import as a separate offline tool if required. | Dependency graph and built native distribution contain no Mesos jars/native libraries/eggs; import scans have only documented legacy schema/import exceptions. No runtime discovery of Mesos sandbox paths. |

Phases 1 and 2 are separable engineering work, but real launch in phase 3 depends on both. Production HA is not required to finish the Pi prototype. No simultaneous dual-write to Mesos log and SQL is recommended: partial commits would create a new consistency problem.

During cutover, preserve framework ID and old snapshot in the rollback archive, but do not reuse Mesos agent IDs as native enrollment IDs. Preserve public task/job history and distinguish migrated historical attempts from new native executions. Freeze cron triggers and updates around export; restoring templates does not prove which time slots ran. Import `ThriftBackfill` semantics and schema versions, deduplicated task configurations, update history, quota and maintenance requests. Never initialize a new empty log over the old cluster as a repair or migration step.

Rollback before native execution can restore the old scheduler/backend from its consistent snapshot. After native workloads start, rollback is a controlled reverse migration: stop/fence native attempts, reconcile outcomes and restore equivalent desired state. Replaying the old snapshot blindly would resurrect obsolete tasks and omit accepted changes. Live executor handoff between Mesos and the agent is deferred; it is a separate hard problem, not a phase-5 assumption.

New acceptance tests must inject crashes before/after every durable-intent and acknowledgement boundary; duplicate/reorder starts, stops and statuses; return stale node inventories; lose the leader/database connection; fill disks; corrupt/truncate journal tails; reboot a node with surviving runtime state; restore an old scheduler backup; and partition an old scheduler plus worker from the new leader. Principal risks are hidden Mesos resource/runtime guarantees, uncommitted side effects in the existing storage model, duplicate external workload effects during partitions, state-schema compatibility, and preserving Python/Thermos behavior while modernizing the worker. Mitigate by narrow capability admission, SQL/outbox first, explicit partition modes, offline import verification and independent protocol fixtures. Production untrusted workloads additionally require an audited runtime boundary, certificate enrollment/rotation, job-to-user authorization, controlled artifact access and authenticated diagnostics; a root-capable experimental runner is not that boundary.

Unverified here: ARM64 availability and compatibility of the future JDBC/gRPC/runtime dependencies; actual Pi cgroup/storage/power-loss behavior; a buildable legacy toolchain; current workload reliance on AppC, custom executors, revocable resources or early discovery registration; acceptable production scale/RPO/RTO; and physical/workload fencing infrastructure. Resolve these at the stated phase gates. They do not prevent choosing the minimal architecture, but they prevent claiming production readiness.
